# Tax planner consolidated browser QA

## Scope and verdict

Browser-only QA of the local public planner, using synthetic figures and the published local **2027–28** rule pack. This consolidates the unresolved findings from the preceding browser passes and the subsequent checks. The 2026–27 Nirdeshika was used for scenario context in the earlier pass; its year-specific figures are not a numerical oracle for this active pack. This is not an independent legal certification.

**Coverage is substantial but not exhaustive.** The matrix below distinguishes actual browser observations from untested combinations. The active pack says filing balances are unavailable, so settlement outcomes cannot be tested in this configuration. The original browser review changed no code or rule packs. The follow-up repair below changes the local frontend, guide and regression tests; it changes no backend formulas, database data, production configuration or published rules.

## Original findings

1. **Income-scope limitation — high product impact.** Entering foreign/treaty income, conditional-exemption income, property gain, precious-metal gain, partnership/association income, final-tax income, restricted-credit income or income requiring classification produced no annual estimate and identified each source for separate review. This is safe withholding, but users with these sources cannot obtain a complete planner result. Decide which sources to support and state the limitation before users invest time entering them.
2. **Filing-balance limitation — high product impact.** The active pack reports filing calculations unavailable even though users can enter withholding and other tax payments. The annual estimate remains available, but a balance/refund cannot be validated in this configuration. Clarify the purpose and availability of this entry point; verify supported settlement against a properly configured non-production pack separately.
3. **Mobile navigation consumes the viewport — medium UX.** At 320 × 568 and 390 × 844, the app header and stacked Wealth navigation occupy substantial space while scrolling and obscure content near the top. No horizontal overflow was observed at the checked widths. Reduce the persistent vertical footprint while retaining navigation and language actions.
4. **Excluded dated donation is not explained near the input — medium UX.** A CZM payment outside the income period was excluded, but the reason was found only after opening Calculation details → Investments, deductions and rebate. Show a concise inline period/exclusion message, and keep the detailed explanation.
5. **Expense edits reset qualification — low UX.** Changing a financial expense amount or type reset its deductibility answer to “Not sure,” resulting in a review warning until reconfirmed. Reconfirmation may be intentional; make the reset and required next action apparent near the field.

The earlier issues around blank CZM entries, rebate explanations and zero-tax wording were addressed in the previous implementation pass and are not counted as open here.

## Recommended follow-up verification

- Review the current rules and sources with a qualified tax reviewer before treating observed arithmetic as authoritative. Check each slab edge, category-specific cap and cross-source rule independently.
- Exercise remaining insurance beneficiary, maturity, fund certification, repeated contribution and recipient combinations, as well as income/date and numerical boundary cases, with expected outcomes recorded before input.
- Use an isolated, suitably configured settlement-capable environment to test withholding, advance tax, final/restricted credits, filing dates, overpayment and unavailable/unknown states. Do not change the user's active pack just to make this test possible.
- Recheck the reported mobile obstruction at 320, 390 and wider desktop sizes after a UI repair, in both languages.
